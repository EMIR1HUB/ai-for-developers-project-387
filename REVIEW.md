# Критерии ревью

Эти критерии читает независимый ревьюер (`.github/workflows/review.yml`) и любой агент или человек, который проверяет PR. Правила кода и устройство проекта — в [AGENTS.md](AGENTS.md), поведение календаря — в [README.md](README.md).

## Что сверить в первую очередь

1. **Согласованный объём.** Описание PR ссылается на исходное обращение, спецификацию, тикеты и комментарий согласования. Изменение делает то, что записано в спецификации, и не больше. Если ссылки нет, она не открывается или изменение выходит за объём, это замечание, а не догадка о намерении.
2. **Сценарии спецификации покрыты тестами:** основной, негативный и соседний, поведение которого сохраняется. Тест проверяет видимое пользователю поведение, а не внутреннее устройство.
3. **Результаты CI** для текущего head SHA PR. Сообщение «тесты прошли» без прогона ничего не доказывает.

## Правила календаря, нарушение которых — дефект

- Занятый слот не должен оставаться доступным для повторного бронирования. Пересечения запрещены по интервалу `[start, end)`, в том числе частичные и между разными типами встреч, и в том числе для одновременных запросов: между поиском слота и `store.addBooking` нет `await` (ADR-0002).
- Сервер принимает только начало слота, который сейчас предлагает ручка слотов (`findOfferedSlot`); начавшийся слот не предлагается.
- Время — в поясе владельца `Asia/Almaty` со смещением `+05:00`. Фронтенд показывает время из строки ответа и не пересчитывает его в пояс браузера.
- «Сейчас» берётся только из часов `now` в `AppContext`, а не из системных часов.
- Ошибки отдаются через `sendError`/`ApiFailure` с кодом из `ErrorCode`; статус следует из кода.
- Контракт меняется только в `api/main.tsp`, `api/openapi.yaml` перегенерирован и закоммичен, сгенерированный код руками не правится.
- Фронтенд ходит в API только через сгенерированный SDK.

## Глубина проверки по риску

Риск определяется последствиями ошибки, а не числом изменённых строк.

| Изменение                                         | Что проверить перед мержем                                                                       |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Текст, подпись, вёрстка                           | Соответствие тексту задачи и отображение в интерфейсе                                            |
| Показ данных на фронтенде без смены API           | Основной и негативный сценарии, соседние экраны не изменились                                    |
| Расчёт слотов, бронирование, проверка пересечений | Основной сценарий, пересечения бронирований, граница окна записи и рабочих часов, конфликт `409` |
| Контракт API                                      | Перегенерация, совместимость фронтенда, тесты контракта                                          |
| Права GitHub Actions, секреты, воркфлоу агента    | Изменение доступа к коду и секретам — отдельное решение человека                                 |

## Формат ревью

- Каждое замечание: **файл и строка**, условие, при котором возникает ошибка, и её последствие для гостя или владельца. Без файла и строки это вопрос, а не замечание.
- Отдельно отметь: соответствует ли изменение спецификации, есть ли изменения вне объёма, каков риск по таблице выше и достаточна ли проверка для него.
- Если подтверждённых дефектов нет, так и напиши: «Подтверждённых дефектов нет». Не придумывай замечания ради количества.
- Форматирование и стиль проверяет линтер в CI, повторять его вывод не нужно.
- При повторном ревью учитывай уже разобранные в PR замечания и проверяй новые правки и затронутое ими поведение.
