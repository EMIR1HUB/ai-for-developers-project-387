## Сценарий

Две роли: **владелец** (один, задан заранее, без авторизации) и **гость** (без регистрации).

### 1. Владелец создаёт тип встречи

1. Открывает «Админка» → «Типы встреч»: список созданных типов и форма нового.
2. Заполняет идентификатор (`intro-15`, под полем видно будущий адрес `/book/intro-15`), название («Встреча 15 минут»), описание и длительность (15 мин), нажимает «Создать тип встречи».
3. Видит уведомление «Тип встречи создан». Тип появляется в списке в админке и на публичной странице «Записаться». Если идентификатор занят или поле заполнено неверно, ошибка показывается под полем.

### 2. Гость записывается на звонок

1. На главной нажимает «Записаться».
2. Видит карточку владельца и список типов встреч (название, описание, длительность) и выбирает тип.
3. Открывается календарь на ближайшие 14 дней. Дни вне окна недоступны, у остальных дней показано число свободных слотов.
4. Выбирает дату. Справа появляется список слотов длительностью выбранного типа со статусом «Свободно» или «Занято».
5. Выбирает свободный слот и нажимает «Продолжить».
6. Вводит имя, email и, по желанию, заметку, затем нажимает «Забронировать». Неверные поля подсвечиваются ошибкой под полем; «Назад» возвращает к выбору времени без потери введённого.
7. Видит экран «Бронирование создано»: тип встречи, дата и время с поясом, имя и email, кнопка «К каталогу». Если слот успели занять, гость видит «Это время уже заняли. Выберите другой слот» и возвращается к выбору времени: слоты обновлены, введённые данные сохранены.

### 3. Владелец видит запись

1. Открывает «Админка» → «Предстоящие бронирования».
2. Видит новую запись в таблице: дату и время (по поясу владельца, с подписью «Время указано по Алматы (UTC+5)»), тип встречи, имя и email гостя, заметку. В таблице бронирования всех типов, которые ещё не закончились (в том числе идущее сейчас), по возрастанию времени начала. Если их нет — «Предстоящих бронирований нет». На телефоне таблица прокручивается по горизонтали.

## Требования

### Обязательные функции

- Владелец: создание и просмотр типов встреч (название, описание, длительность), список предстоящих бронирований всех типов.
- Гость: список типов встреч, календарь доступности на 14 дней, бронирование свободного слота.

### Правила бронирования

- Всё время в часовом поясе владельца `Asia/Almaty` (UTC+5), гость видит время в нём. API отдаёт время в ISO 8601 со смещением владельца (`2026-11-24T09:00:00+05:00`), принимает любое ISO-время со смещением или `Z`; время без смещения — `422` ([решение](https://github.com/EMIR1HUB/ai-for-developers-project-386/issues/3)).
- Окно записи: сегодняшняя дата по часовому поясу владельца и ещё 13 дней, сдвигается со временем. Слот доступен, только если его начало строго позже текущего момента.
- Рабочие часы: ежедневно, включая выходные, 09:00–18:00. Слот целиком помещается в рабочие часы.
- Длительность типа встречи кратна 15 минутам, от 15 до 240. Длительность слота равна длительности типа, слоты начинаются с шагом 15 минут.
- Пересечения запрещены, в том числе частичные и между разными типами. Бронирование может начинаться ровно в момент окончания предыдущего (интервал `[start, end)`).
- Правила действуют и для одновременных запросов: из двух конкурирующих бронирований одного времени проходит одно, второе получает конфликт.
- Бронирование создаётся `POST /api/bookings` с `{ eventTypeId, start, guestName, guestEmail, note? }`, конец считает сервер; ответ `201` с бронированием. Принимается только `start`, совпадающий с началом слота, который сейчас предлагает ручка слотов (иначе `422 SLOT_NOT_OFFERED` с причиной: уже началось, вне окна записи, не на сетке 15 минут, вне рабочих часов); пересечение — `409 SLOT_TAKEN` «Это время уже заняли. Выберите другой слот». Защиты от повторной отправки нет: повтор того же бронирования получает `409` ([решение](https://github.com/EMIR1HUB/ai-for-developers-project-386/issues/6)).
- Гость указывает имя и email (обязательно) и заметку (по желанию). Владелец видит предстоящие бронирования, то есть ещё не закончившиеся, по времени начала.

### Ограничения

- Один владелец, задан заранее. Нет авторизации, личных кабинетов, внешних календарей и уведомлений.
- Список бронирований с именами и email гостей доступен без авторизации: это следствие отсутствия авторизации по заданию.
- Типы встреч только создаются и просматриваются: редактирования и удаления нет. Бронирование нельзя отменить или изменить.
- **Данные хранятся в памяти процесса: перезапуск сбрасывает все типы встреч и бронирования.** Сервис работает в одном экземпляре ([ADR-0002](docs/adr/0002-in-memory-single-process-storage.md)). Чтобы каталог после перезапуска не был пустым, при старте создаются два демо-типа встреч (`intro-15`, `call-30`); это отключается переменной окружения `DEMO_DATA=false`, в тестах демо-данных нет ([решение](https://github.com/EMIR1HUB/ai-for-developers-project-386/issues/7)).
- Приложение собирается в Docker-образ и запускается в контейнере по порту из `PORT`, без базы данных и других внешних сервисов ([«Деплой»](#деплой)).

### API и генерация кода

- Контракт описан на TypeSpec. Из него генерируется OpenAPI-спецификация, а из неё клиентский SDK для фронтенда.
- До выбора стека нужно проверить, что для языка фронтенда есть генератор клиента из OpenAPI.
- Серверные типы и маршруты генерируются, если фреймворк это поддерживает. Если нет, бэкенд пишется по контракту и проверяется тестами ([ADR-0001](docs/adr/0001-contract-first-typespec-hey-api.md)).
- Ручки: `GET /api/owner`, `GET`/`POST /api/event-types`, `GET /api/event-types/{id}`, `GET /api/event-types/{id}/slots`, `GET /api/bookings` (предстоящие, по возрастанию начала), создание бронирования, `GET /api/health`. Списки — массивы без пагинации, типы встреч в порядке создания. Поля моделей — в [решении](https://github.com/EMIR1HUB/ai-for-developers-project-386/issues/5).
- Профиль владельца (имя, подпись, часовой пояс) задан в конфиге бэкенда (`backend/src/ownerProfile.ts`) и отдаётся через `GET /api/owner`; аватар — статичная картинка фронтенда (`frontend/public/owner-avatar.svg`).
- Идентификатор типа встречи задаёт владелец при создании: строчные латинские буквы, цифры и дефис, 3–50 символов (например, `intro-15`); занятый идентификатор — `409`. Страница гостя — `/book/<id>`. Бронированию идентификатор (UUID) назначает сервер ([решение](https://github.com/EMIR1HUB/ai-for-developers-project-386/issues/2)).
- `GET /api/event-types/{id}/slots` возвращает все слоты окна записи по возрастанию начала с признаком `available` (`false` — слот уже начался или пересекается с бронированием). Начавшиеся слоты остаются в списке недоступными, поэтому сегодняшний день после последнего слота остаётся в календаре с нулём свободных. Число свободных слотов по дням считает фронтенд.
- Ошибки передаются HTTP-статусами: `409` занятый слот, `422` валидация, `404` неизвестный тип встречи ([ADR-0003](docs/adr/0003-standard-http-status-codes.md)). Тело любой ошибки — `{ code, message, fields? }`: `code` из закрытого перечисления, `message` — русский текст для пользователя, `fields` (только в `422`) — все ошибочные поля `{ field, message }`. Нечитаемый JSON или тело не JSON-объект — `400`, неизвестный адрес `/api` — `404`, непредвиденная ошибка — `500` без деталей ([решение](https://github.com/EMIR1HUB/ai-for-developers-project-386/issues/4)).

## Стек

- **Контракт:** TypeSpec (`api/main.tsp`) → OpenAPI 3.1 (`api/openapi.yaml`, коммитится).
- **Бэкенд** (`backend/`): Node.js 24 + Fastify, TypeScript запускается напрямую (type stripping). Типы контракта генерирует Hey API.
- **Фронтенд** (`frontend/`): Vite + React + Mantine (календарь — `@mantine/dates`). Клиентский SDK генерирует Hey API.
- **Тесты:** Vitest, браузерные сценарии — Playwright (Chromium). **Линтеры:** oxlint, oxfmt, actionlint. **Коммиты:** Conventional Commits, проверяет commitlint. **Релизы:** release-please.
- **Окружение:** mise (версии инструментов, задачи, dev-серверы через daemons), git-хуки через hk.

## Установка

Нужен [mise](https://mise.jdx.dev/getting-started.html).

```bash
git clone https://github.com/EMIR1HUB/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install
```

`mise install` ставит Node, hk, pitchfork и actionlint нужных версий, затем через postinstall-хук выполняет `npm ci`, скачивает Chromium для браузерных тестов (`mise run browsers`) и устанавливает git-хуки (`hk install`). Системные библиотеки для Chromium хук не ставит: на Linux без них браузер не запустится, их ставит `npx playwright install --with-deps chromium` (нужен sudo).

## Использование

| Команда                                | Что делает                                                                                           |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `mise run dev`                         | Генерирует код из контракта и запускает бэкенд (`:3000`) и фронтенд (`http://localhost:5173`) в фоне |
| `mise daemons ls` / `logs` / `stop`    | Состояние, логи и остановка dev-серверов                                                             |
| `mise run generate`                    | TypeSpec → `api/openapi.yaml` → типы бэкенда и SDK фронтенда                                         |
| `mise run check`                       | Все проверки: линтеры, типы, тесты, браузерные сценарии. Эту же команду запускает CI на каждый push  |
| `mise run e2e`                         | Собирает фронтенд и прогоняет браузерные сценарии Playwright на сервере `:4173` без демо-данных      |
| `mise run browsers`                    | Скачивает Chromium для браузерных сценариев (делает postinstall-хук `mise install`)                  |
| `mise run lint` / `typecheck` / `test` | Проверки по отдельности                                                                              |
| `mise run format`                      | Автоисправление линтеров и форматирование                                                            |

**Собранный фронтенд с одного сервера.** В dev фронтенд отдаёт Vite, а в браузерных тестах (и в контейнере) собранный `frontend/dist` раздаёт сам Fastify, если задана переменная `STATIC_DIR`. Адреса страниц вне `/api` (`/book/<id>`, `/admin`) получают `index.html`, неизвестный адрес под `/api` по-прежнему отвечает JSON `404 NOT_FOUND`. Запуск вручную:

```bash
npm run build -w @calendar/frontend
STATIC_DIR=../frontend/dist npm start -w @calendar/backend  # http://localhost:3000
```

**Браузерные сценарии** (`e2e/tests/`) идут на настоящем сервере без подмены ответов API: `mise run e2e` собирает фронтенд, Playwright запускает сервер на `127.0.0.1:4173` с `DEMO_DATA=false` и останавливает его после прогона. Порт должен быть свободен: чужой сервер на нём не переиспользуется. Сценарии работают на реальном времени и берут слот из ответа ручки слотов. Один сценарий: `npm run e2e -w @calendar/e2e -- -g "<имя теста>"` (после `npm run build -w @calendar/frontend`). Если сценарий упал в CI, отчёт Playwright со следами лежит в артефакте `playwright-report` прогона.

## Деплой

Приложение упаковано в Docker-образ ([`Dockerfile`](Dockerfile)) и выкатывается на [Render](https://render.com) бесплатным тарифом. Образ один на все среды: локально, в CI и на хостинге он запускается одинаково.

**Публичная ссылка:** https://calendar-5rm2.onrender.com (проверка готовности: `/api/health`). Сервис создан из исходного проекта и выкатывается из его ветки `main`; изменения этого репозитория на нём не появятся, пока сервис не пересоздан по `render.yaml` отсюда. После простоя больше 15 минут бесплатный сервис засыпает, первый запрос просыпается до минуты, а данные в памяти сбрасываются.

### Образ

Многостадийная сборка на `node:24.22.3-slim` (версия как в `mise.toml`): первая стадия генерирует SDK и собирает фронтенд, вторая ставит только прод-зависимости бэкенда, итоговый образ запускает `node backend/src/server.ts` без сборки бэкенда от непривилегированного пользователя `node`. Собранный фронтенд раздаёт сам Fastify (`STATIC_DIR=/app/frontend/dist`), отдельного веб-сервера нет.

```bash
docker build --tag calendar .
docker run --rm --env PORT=8080 --publish 8080:8080 calendar  # http://localhost:8080
```

Порт читается из переменной `PORT` (по умолчанию 3000), сервер слушает `0.0.0.0`. Render задаёт `PORT=10000` сам. Внешних зависимостей нет: при старте создаются демо-типы встреч, хранилище лежит в памяти процесса. CI на каждый push собирает образ, запускает контейнер на порту 8080 и проверяет `/api/health`, страницу `/`, JSON `404` под `/api` и демо-данные (job `docker` в `ci.yml`).

### Данные после перезапуска

**Все типы встреч и бронирования хранятся в памяти и сбрасываются при каждом перезапуске контейнера** ([ADR-0002](docs/adr/0002-in-memory-single-process-storage.md)). Бесплатный сервис Render засыпает после 15 минут без запросов: процесс останавливается, первый запрос просыпается около минуты, и данные пропадают так же, как при перезапуске. Демо-типы `intro-15` и `call-30` создаются заново при каждом старте.

### Создание сервиса на Render

Сервис создаётся один раз по [`render.yaml`](render.yaml) (Blueprint): Docker, бесплатный план, health check `/api/health`, автодеплой с ветки `main`.

1. Войдите в Render, подключите GitHub-аккаунт и дайте доступ к репозиторию.
2. New → Blueprint, выберите этот репозиторий. Render прочитает `render.yaml`, настройки заполнять не нужно.
3. После первой сборки откройте адрес сервиса `https://<имя>.onrender.com`. Каждый следующий коммит в `main` выкатывается автоматически.

Render MCP (ниже) не умеет создавать сервис в Docker-режиме или из готового образа, поэтому первый шаг делается в дашборде. Деплои, логи, переменные окружения и статус через MCP доступны.

### Подключение Render MCP (без секретов)

Проектный [`.mcp.json`](.mcp.json) описывает сервер `https://mcp.render.com/mcp`, ключ в него не записан: заголовок берёт значение из переменной окружения.

1. Создайте API-ключ: Render → Account Settings → API Keys. Лучше отдельный ключ для этого проекта: MCP получает доступ ко всем сервисам выбранного workspace, включая смену переменных и запуск деплоев.
2. Экспортируйте его в оболочке, из которой запускается Claude Code. Ключ не попадает в Git, файл с ним не создаётся:

   ```bash
   export RENDER_API_KEY=<ключ>
   claude
   ```

3. Подтвердите проектный сервер при первом запуске и проверьте подключение: `claude mcp list` (или `/mcp` в сессии), у `render` должен быть статус `Connected`. Если переменная не задана, в заголовок уйдёт буквальный текст `Bearer ${RENDER_API_KEY}` и подключение не удастся.
4. В сессии выберите workspace: «Set my Render workspace to <имя>».

Без ключа можно войти через OAuth: `/plugin install render@claude-plugins-official`, при первом использовании откроется авторизация в браузере. Данные сессии хранятся у Claude Code, в репозиторий они не попадают.

## Релизы

Релизы выпускает [release-please](https://github.com/googleapis/release-please) (`.github/workflows/release-please.yml`) по Conventional Commits. Версия одна на весь репозиторий.

1. После каждого push в `main` release-please открывает или обновляет релизный PR `chore(main): release X.Y.Z`. В нём следующая версия, новые записи `CHANGELOG.md`, версия в корневом `package.json`, `package-lock.json` и `.release-please-manifest.json`.
2. Версию определяют коммиты после прошлого релиза: `fix:` даёт patch, `feat:` даёт minor. Пока версия ниже `1.0.0`, ломающее изменение (`feat!:`) тоже даёт minor. Если есть только `docs:`, `chore:`, `test:`, `refactor:`, релизный PR не появляется. Коммиты не по Conventional Commits пропускаются.
3. Слияние релизного PR ставит тег `vX.Y.Z` и создаёт GitHub Release с тем же changelog.

Настройки лежат в `release-please-config.json`: стартовая версия `0.1.0` (в манифесте), changelog собирается из коммитов после `bootstrap-sha`. `CHANGELOG.md` и `.release-please-manifest.json` руками не правят. PR лучше вливать squash-merge с заголовком по Conventional Commits: заголовок станет коммитом в `main` и строкой changelog, а хук commitlint коммиты, созданные на GitHub, не проверяет.

**Ограничение CI на релизном PR.** Релизный PR создаётся от имени `GITHUB_TOKEN`, а события от этого токена не запускают другие workflows. Поэтому `ci.yml` на релизном PR сам не запускается, и проверок у него нет. В нём меняются только `CHANGELOG.md`, версии и манифест, а CI отработает на `main` после слияния. Если проверки на релизном PR понадобятся, нужен fine-grained PAT в секрете и вход `token:` у action.

**Разовая настройка владельцем.** Без неё `GITHUB_TOKEN` не может создать PR и workflow упадёт: Settings → Actions → General → Workflow permissions → включить «Allow GitHub Actions to create and approve pull requests».
